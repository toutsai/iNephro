# 20-JUDGMENT：判斷力 rubric（弱模型可執行版）

> 每條判準附正例／反例。原則：**能寫成判準的照判準走；寫不成判準的
> （品味、模糊題）不要硬判，走「升級或問人」路徑。**

## R1. 何時該升級模型（配合 10-DISPATCH §5）
升級訊號（任一成立即升級）：
- 同一錯誤修了兩次還在（不是兩個不同錯誤，是同一個）。
- 你發現自己在「猜」：沒有證據支持 A 或 B，卻打算選一個試試。
- 任務涉及取捨且兩邊都有道理（架構選型、API 設計、刪不刪某機制）。
- 涉及醫療內容語意（這種情況升級後通常還要問使用者，見 R3）。

✅ 正例：修 TTS bug，第一次改 onend 沒效，第二次加輪詢還是沒效 →
帶兩次失敗軌跡升 opus。
❌ 反例：測試失敗一次，錯誤訊息明確指出是 import 路徑打錯 → 這是新資訊
指路，自己修即可，升級反而浪費。**有明確下一步的失敗不觸發升級。**

## R2. 何時算真的完成（Definition of Done）
全部成立才算完成：
1. 使用者要求的每一項都有對應產出（逐條對照原始要求，不是「大致都做了」）。
2. `npx vite build && npx vitest run` 通過（有碰程式碼時）。
3. 變更已 commit + push 到正確分支。
4. M/L 級：fresh-context 覆核通過。
5. CLAUDE.md「目前狀態」已更新（有實質變更時）。

✅ 正例：改了 eGFR 計算器 → 測試綠、build 過、commit、覆核 agent 確認
公式與 KDIGO 分期對照無誤、進度已記 → 完成。
❌ 反例：「程式碼寫好了，build 也過了，測試等使用者自己跑」→ 未完成。
❌ 反例：功能做完但只在回覆裡描述、沒 commit → 未完成（session 中斷即歸零）。

## R3. 何時該停下來問使用者（用 AskUserQuestion，附具體選項）
**必問**（不問直接做算違規）：
- 改動會影響醫療內容的語意（衛教答案、營養分級門檻、eGFR 公式/分期）。
- 破壞性且難回復：刪檔案、改資料庫/快取結構、改 CSP 或安全機制、force push。
- 需求有兩種以上合理解讀，且做錯的返工成本 > 問一次的成本。
- L 級計畫完成時（CLAUDE.md 規定要等確認）。

**不問直接做**（問了反而礙事）：
- 可逆、且是原始需求的自然延伸（改字體大小順手修同一行的 lint 錯）。
- 技術實作細節有慣例可循（變數命名、檔案放哪個既有目錄）。

✅ 正例：使用者說「營養查詢結果加個警示」——警示的醫療措辭有多種寫法 →
擬 2–3 個措辭選項問使用者。
❌ 反例：「幫我把按鈕改大一點」→ 跑去問「請問要改多少 px？」——先改成
合理值（如 +20%），回報時說明可再調。**能給合理預設的不要問。**

## R4. 方向錯了的訊號（該換路，不是再重試）
出現任一訊號，停止當前路線，回到上一個決策點想別的走法：
- 修 A 壞 B、修 B 又壞 A（在打地鼠 = 動錯了層級）。
- 為了讓方案成立，需要的「例外處理」越來越多（第 3 個特例出現就停）。
- 你開始想繞過驗證（跳過某測試、放寬驗收條件）來讓它過。
- 實際工時已是預估的 3 倍且看不到收斂。

✅ 正例：為了在 Edge Function 做串流，連續加了 polyfill、改 header、
換 runtime 都失敗 → 訊號齊了：平台不支援（CLAUDE.md 技術地雷有寫），
換路做「假串流」（分段輪詢渲染）並回報原因。
❌ 反例：測試失敗，把該測試 `skip` 掉讓 CI 綠 → 這是繞過驗證，禁止。

## R5. 品質底線怎麼驗（最低配備，不可再減）
| 產出類型 | 底線驗法 |
|----------|----------|
| 程式碼變更 | build + vitest 綠；改到的功能至少一條路徑實際跑過或有測試覆蓋 |
| UI/CSS 變更 | 亮色+暗色兩種主題都檢查；1024px 斷點上下各看一次（本專案使用者多為年長者：字體不得縮小、對比不得降低）|
| 文件/規則檔 | fresh-context read-back：存在、完整、無內部矛盾、路徑與工具名真實存在 |
| API 變更 | `src/test/apiSecurity.test.js` 綠；速率限制與 CORS 行為未被弱化 |
| 醫療相關內容 | 不自行生成醫療事實；來源只能是既有內容、使用者提供、或標明出處的權威來源（如 NKF/KDIGO），並問過使用者 |

## R6. 補不了的事（誠實條款）
拆解、驗證、多樣本評審能補**執行品質**；以下補不了，遇到照此處理：
- **品味判斷**（視覺美感、文案語氣）：產 2–3 個方案 → 問使用者選。
  不能問時選最保守（最接近現狀）的，並在回報標注「品味判斷，信心低」。
- **模糊需求**：不要靠腦補收斂。一次把歧義列成選項問完（R3）。
- **超出能力**：兩輪＋升級後仍無解 → 明說做不到＋失敗軌跡＋建議
  （找外部第二意見／換方向／等更強模型 session）。**編一個看起來能動的
  答案比承認做不到嚴重得多。**
