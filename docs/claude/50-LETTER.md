# 50-LETTER：給未來 session 的信

> 寫於 2026-07-06，Fable 5 制度建立 session。使用者明說之後的 session
> 由較小的模型長期運作，所以這封信寫給「能力普通但照規則走」的你。

## 三件使用者沒問、但對這個環境最重要的事

### 1. 這個專案的真正風險在醫療內容與年長使用者，不在程式碼
這是給台灣腎臟病患（多為年長者）的衛教網站。一個 CSS bug 的代價是難看；
一句錯誤的鉀離子建議的代價是傷人。所以優先序永遠是：
醫療語意正確 > 無障礙（大字體、高對比、簡單操作）> 效能 > 視覺美感。
repo 裡已有 P0 醫療安全 guardrails（`api/_shared/security.js`）——任何
「順手簡化」都不准碰它。當技術上的漂亮做法與年長者易用性衝突時，
選後者，不用問。

### 2. 使用者的工作模式：高授權、要進度落地、session 常中斷
使用者授權高自主（本機環境甚至授權自動部署 master），不喜歡被逐步請示；
但他非常在意**中斷時已落檔的就是全部**。所以：小步 commit+push、先做價
值最高的、每完成一項立刻寫檔。與其做到 90% 沒 commit，不如做到 60% 已
push。回報用結論先行的完整句子，他讀中文（台灣繁體）。

### 3. token 是這個環境的第一稀缺資源
未來的你比寫這封信的我便宜，但也更容易被大 context 淹沒而失焦。這套制度
（DISPATCH 的外包規則、模板的回報合約）本質上都在保護主 context。當你
覺得「這次直接自己讀比較快」的時候，通常是對的一兩次、然後在第三次把
context 塞爆。照規則走：3 個檔案以上的理解工作就外包。

## 這套制度最可能的退化方式與預防

1. **規則檔膨脹成沒人讀的長文** → 每個 session 往裡加一點，最後弱模型
   乾脆全部跳過。預防：40-MAINTENANCE 的行數門檻是硬規則，超了就精簡；
   加新規則時優先問「能不能改一條舊的，而不是加一條新的」。
2. **儀式化執行**：照抄流程但不看規模——給 S 級小事跑 L 級流程（浪費），
   或把 L 級大事判成 S 級（危險）。預防：判級時取「最嚴重的一項」；
   判錯級被糾正過就寫進 LESSONS。
3. **驗收條件空洞化**：模板抄了，但驗收條件填成「功能正常運作」這種
   不可判定的話。預防：驗收條件必須可機械判定（命令會過／行為可觀察／
   檔案存在）；fresh-context 驗收者發現條件不可判定時，應回報「條件
   無法驗收」而不是硬給 ✅。
4. **文件與現實脫節**（本次診斷的 #2 重演）：progress 沒更新、路徑改了
   路由表沒跟上。預防：session 收尾清單是硬規則；發現脫節的人有責任
   當場修（這屬於「可自行改」）。
5. **規則衝突時亂猜**：新指令與制度檔打架。預防：優先序固定為
   harness session 級指令 > CLAUDE.md > docs/claude/*；衝突本身記入
   LESSONS。

## 誠實條款（對你，也是對使用者）
這套制度補得了執行品質（漏讀、失焦、不驗證），補不了品味與模糊題的
判斷力。遇到品味題：出方案讓使用者選。遇到模糊題：把歧義列成選項一次
問完。遇到超出能力的：說做不到，附失敗軌跡。在這個環境裡，編造一個
看起來對的答案，比承認做不到的後果嚴重得多——尤其這是醫療網站。
