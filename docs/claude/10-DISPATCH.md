# 10-DISPATCH：模型調度守則

> 讀者：本 repo 的主對話模型（通常是 Sonnet 等級）。目的：主 context 只留
> 決策與結論，粗活與大量文字全部外包給 subagent。

## 0. 先確認本 session 實際可用什麼（不要憑印象）
每個 session 的可用資源寫在 system prompt 的工具定義與 `<system-reminder>` 裡：
- **subagent 類型**：看 "Available agent types" 清單。本文撰寫時有：
  `Explore`（搜尋用，不做編輯）、`Plan`（規劃）、`general-purpose`（多步任務）、
  `claude`（萬用）、`claude-code-guide`（Claude Code 用法問答）。
- **model 參數**：`Agent` 工具的 `model` 欄位，撰寫時可選
  `haiku` / `sonnet` / `opus` / `fable`。`fable` 只在特殊 session 出現，
  **預設不要指定它**；不確定就省略 model 參數（省略 = 繼承主對話模型，
  永遠是安全選擇）。
- **effort 參數**：`Agent` 工具**沒有** effort 參數，不要嘗試傳。
  （部分 session 另有 `Workflow` 多代理編排工具，其 `agent()` 才有 effort；
  它需要使用者明確要求才能用，且不是每個 session 都有——工具清單裡沒看到
  就當它不存在。日常派工一律用 `Agent` 工具。）
- 若清單與本文不符，**以 session 內的清單為準**，並依 `40-MAINTENANCE.md`
  更新本檔。

## 1. 指揮官不下場
主對話（你）只做：判級、派工、讀回報、做決策、對使用者說結論。
以下工作**一律派 subagent**，主對話不親手做：
- 需要看 3 個以上檔案的搜尋／理解（派 `Explore`）
- 掃整個 repo 或整個目錄（派 `Explore`，指明搜尋廣度 "medium" 或 "very thorough"）
- 查網頁／文件研究（派 `general-purpose`，它有 WebSearch/WebFetch）
- 批次改多個檔案的機械性修改（派 `general-purpose` 或多個並行）
- 審查大 diff（派 fresh-context `general-purpose`）

主對話**可以**親手做：讀單一小檔的目標段落、單檔小 Edit、跑驗證命令、git 操作。

**判準**（兩個門檻並存，管的是不同東西）：
- 單一檔案 >400 行 → 禁止整檔 Read（改用 Grep 定位＋分段 Read，見 00-DIAGNOSIS #1）。
- 同一件事**累計**預估會讓 >~200 行原文進入主 context → 整件事外包給 subagent
  （即使每個檔案都不到 400 行）。

並行派工時，把互不依賴的 Agent 呼叫放在同一則訊息裡同時發。

## 2. 派工三件套（缺一不派）
每個派工 prompt 必含（可直接套 `30-TEMPLATES.md` 的模板）：
1. **目標與動機**：要做什麼、為什麼（subagent 看不到主對話，背景要自帶）。
2. **驗收條件**：可機械判定的完成標準（「build 通過且新測試綠」，
   不是「做好做滿」）。
3. **回報格式**：明確規定回什麼、不回什麼。

## 3. 回報合約（寫進每個派工 prompt 的固定結尾）
> 回報規則：只回結論、關鍵證據（檔案:行號）、與驗收條件的逐條對照。
> 不要貼大段程式碼或檔案原文。超過 30 行的產出（報告、清單、log）寫到
> 檔案裡，回報路徑即可。若失敗，回：嘗試了什麼、卡在哪、錯誤訊息原文。

## 4. model 選擇（Agent 工具的 model 參數）
| 選 | 適用 | 範例 |
|----|------|------|
| `haiku` | 機械性、判準明確、單步 | 批次改 import 路徑、跑固定命令收集輸出、格式轉換 |
| 省略（=繼承主模型，通常 sonnet） | 一般搜尋、實作、審查 | Explore 搜尋、寫元件、修 bug |
| `opus` | 難題、升級目標、高風險判斷的第二意見 | 詭異 bug 兩輪未解、架構取捨、醫療內容相關判斷 |

不確定選哪個 → 省略 model 參數。

## 5. 升降級路徑
- **haiku 錯一次**：不重試，直接升 sonnet（省略 model）重派。
- **sonnet 同一子任務連錯兩次**：升 `opus`，且 prompt 必須帶**完整失敗軌跡**
  （兩次各做了什麼改動、跑了什麼驗證、錯誤訊息原文）。不帶軌跡的升級等於
  讓 opus 重走同樣的死路。
- **降級回收**：opus/主模型解出一個「模式」（例：某類呼叫要統一改成新寫法）
  後，把模式寫成具體規則＋一個已完成的範例，交給 `haiku`/sonnet 批次套用
  到其餘位置。
- **重試上限**（計數表，照表執行）：

  | 執行者 | 失敗幾次後動作 |
  |--------|----------------|
  | haiku | 1 次 → 升 sonnet（不重試）|
  | sonnet／主模型 | 2 次（原始＋重試一次）→ 帶失敗軌跡升 opus |
  | opus（升級後） | 2 次 → 停止，向使用者回報失敗軌跡與你的判斷 |
  | 換一種完全不同的做法 | 計數歸零重算，但同一目標整個 session 最多換路 1 次 |

## 6. 驗證不自驗
改動者（包括主對話自己）不得當自己的驗收者。
- **檔案類產出**（文件、設定、計畫）：派 fresh-context agent 做 read-back——
  「讀 X 檔，回答：(1) 是否存在且完整（結尾不是斷句）(2) 是否滿足以下
  驗收條件…（逐條）(3) 有無內部矛盾」。
- **程式碼**：先機器驗（`npx vite build && npx vitest run`；有對應測試就
  加測試），再派 fresh-context agent 讀 diff 對照驗收條件。S 級小改可只做
  機器驗。
- **高風險判斷**（醫療內容、安全機制、刪東西）：加第二意見——派 `opus`
  獨立判一次；或產 2–3 個候選方案後派一個 agent 當評審選優並說明理由。
- fresh-context 的意思：新派一個 agent，prompt 只給驗收條件與必要背景，
  **不給**你已形成的結論，避免它順著你的答案點頭。

## 7. 常見反模式（看到自己在做就停）
- 派了 Explore 之後自己又平行去 Read 同一批檔案（雙倍 token，擇一）。
- 派工 prompt 只有一句「幫我看看 X」（缺三件套）。
- subagent 回報失敗後，用一模一樣的 prompt 原樣重派（違反升級規則）。
- 為了「保險」把整個檔案內容貼進派工 prompt（給檔案路徑就好，subagent 自己會讀）。
- 用 Bash `cat`/`grep`/`find` 做檔案操作（用 Read/Grep/Glob 工具）。
