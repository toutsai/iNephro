# 30-TEMPLATES：派工 prompt 模板

> 用法：複製對應模板 → 填掉所有 `【…】` 佔位 → 用 `Agent` 工具派出。
> **任何 `【…】` 留空就派出，視同違規派工。** model 選擇見 `10-DISPATCH.md` §4。
> 每個模板結尾的「回報規則」段落是固定合約，原樣保留。

## 共用結尾（每個模板最後都要帶）
```
回報規則：只回結論、關鍵證據（檔案:行號）、與驗收條件的逐條對照
（每條標 ✅/❌）。不要貼大段程式碼或檔案原文。超過 30 行的產出寫到
【產出檔案路徑，通常放 scratchpad 或 docs/claude/plans/】，回報路徑。
若失敗：回嘗試過什麼、卡在哪、錯誤訊息原文，不要假裝成功。
```

## T1. 搜尋／理解（subagent_type: Explore——搜尋用，不做編輯）
```
背景：iNephro 是腎臟科衛教網站（React 19 + Vite，api/ 是 Vercel functions）。
我正在【要做的事】，需要先搞清楚【目標機制】。

任務：找出【具體問題，例：TTS 播放結束的偵測邏輯定義在哪、被誰呼叫、
有哪些已知 workaround】。
搜尋範圍：【目錄或「整個 repo」】，搜尋廣度：【medium / very thorough】。

驗收條件：
- 每個結論都有 檔案:行號 佐證
- 明確回答【問題1】【問題2】
- 若找不到，列出你搜過的關鍵字與路徑（證明找過，而不是說「沒有」）
```
（+ 共用結尾）

## T2. 實作（subagent_type: general-purpose）
```
背景：【專案脈絡＋為什麼要做這個，2-3 句。subagent 看不到主對話，
相關的 CLAUDE.md 技術地雷要抄給它，例：3D 骨骼只能用 quaternion】。

任務：實作【功能】。
- 改動範圍限於：【檔案清單】。範圍外的問題不要順手修，記下來回報。
- 遵循現有程式風格（先讀鄰近程式碼再動筆）。

驗收條件：
- 【可觀察的行為改變，例：點 X 按鈕後 Y 出現】
- `npx vite build && npx vitest run` 通過
- 【若適用：新增測試 src/test/【名稱】.test.js 覆蓋【情境】】
不要 commit，改完回報即可（commit 由主對話統一做）。
```
（+ 共用結尾）

## T3. 重構（subagent_type: general-purpose）
```
背景：【為什麼重構、目標形狀】。

任務：重構【範圍】，規則：
- 行為不得改變：重構前先跑 `npx vitest run` 記錄基準，重構後結果必須一致。
- 【具體的目標模式，例：把 X 抽成 hook，介面為 …】
- 一次只做這一種轉換，發現其他可改進處記下來回報，不要動。

驗收條件：
- 測試結果與基準一致、build 通過
- 【結構性驗收，例：App.jsx 不再直接 import three】
- diff 中沒有與本次轉換無關的改動
```
（+ 共用結尾）

## T4. 研究（subagent_type: general-purpose，需要 WebSearch/WebFetch 時用它）
```
背景：【決策脈絡：我們要在 A/B 之間選、或要確認 X 是否可行】。

任務：研究【問題】。
- 優先來源：官方文件 > 官方 repo issues > 高信譽技術文章。醫療主題只准
  用權威來源（NKF、KDIGO、台灣腎臟醫學會等）並附出處連結。
- 區分「查證過的事實」與「你的推論」，分開標示。
- 查不到的就寫查不到，不要補腦。

驗收條件：
- 直接回答【決策問題】並給建議＋理由
- 每個關鍵事實附來源 URL
- 列出主要風險／不確定性
完整研究筆記寫到【檔案路徑】，回報只要結論摘要。
```
（+ 共用結尾）

## T5. 審查／驗收（subagent_type: general-purpose；高風險時 model: opus）
```
你是 fresh-context 驗收者，對以下改動一無所知，請獨立判斷。
背景：【原始需求原文】。改動範圍：【分支名或「git diff master...HEAD」】。

任務：逐條核對驗收條件，並主動找碴：
1. 【驗收條件1】
2. 【驗收條件2】
3. 通用檢查：有無破壞 CLAUDE.md「技術地雷」節的任一條？有無弱化
   api/_shared/security.js 相關防護？UI 改動是否兩主題（亮/暗）都成立？
4. 對每條給 ✅/❌ 與證據（檔案:行號）。找不到問題也要說明你檢查了什麼。

注意：你的任務是找出問題，不是背書。找到 ❌ 就是成功的審查。
```
（+ 共用結尾）

## 並行派工提醒
互不依賴的多個派工，放在**同一則訊息**裡同時發（多個 Agent 工具呼叫），
不要一個等一個。互相依賴的（例：先搜尋才知道改哪）必須等前一個回來。
